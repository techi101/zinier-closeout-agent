    Roadmap

    One agent, one job type, one customer first. Each stage has an exit test so the roadmap can correct itself.

    1. Now weeks 0 to 6

      Ship close-out for fibre repair jobs at one telecom customer, with a confirm screen.

      • Extraction to the job record, every value tied to the phrase it came from
      • Grounding check on light level and sign-off, the two fields where a guess does harm
      • Required-field policy per job type and outcome, held as config
      • Events below shipped on day one, before the model is tuned

      Exit test: back-office correction rate on agent-filled fields is no worse than the form, over 2 weeks.

    2. Next weeks 6 to 12

      Make it part of the job, not a side panel.

      • Voice capture that works offline and syncs later, like the mobile app already does
      • Confirmed parts write to inventory against the task and the van
      • Customer custom fields through Studio, no code
      • Weekly eval on a golden set built from back-office corrections

      Exit test: second customer live on config only, no code change.

    3. Later quarter 2

      Use clean close-out data to move the KPIs customers set in Goals.

      • Revisit reasons and fault codes feed Insights: repeat visits, first-time fix
      • Parts-shortage revisits feed van stock planning
      • French, Spanish and German notes, matching the site's languages

      Exit test: revisits caused by missing parts fall at the pilot customer.

    Entities

    closeout_session
    One per close-out attempt. session_id, task_id, technician_id, job_type, channel (voice or chat), offline flag, model_version, prompt_version, policy_version, started_at, submitted_at.
    closeout_field
    One row per field per session. Value, source (agent, technician, back office), evidence span start and end, grounded true or false, confirmed by technician.
    closeout_prompt
    One row per question asked. Field, question text, answered, answer channel, seconds to answer.
    note_transcript
    Text, speech-to-text confidence, language. Raw audio stays in the lake with a retention rule agreed with Legal, because notes contain customer names and addresses.
    field_policy
    Required fields by job type and outcome. Versioned config that Studio edits, so a consultant can change it without a release.

    Sources read at session start

    • Task record from FSM: job type, asset (ONT serial), SLA due time, schedule slot
    • Van stock from Parts and Inventory, to check that fitted parts exist
    • Field policy for this job type
    • Last close-out on the same asset, to spot a repeat visit

    Warehouse

    • fact_closeout_session grain: one session
    • fact_closeout_field grain: session by field
    • dim_field_policy, dim_model_version slowly changing
    • mart_closeout_quality_daily by customer, job type, model version

    What this is built on

    • zinier.com, Agents: technicians "describe the work", the agent "completes the job record in the approved format, prompting for additional information as needed". Agents are task-focused and work from live FSM data.
    • Zinier blog, Building AI agents that work with your real data: Andrew Wolf on custom fields, and on using rules where rules are enough because Gen AI is "not 100% deterministic". The grounding check here follows that idea.
    • zinier.com, Telecommunications: "the evidence you rely on is incomplete" for SLA reporting, and jobs that take two visits instead of one.
    • Mobile Task Execution (offline support) and Parts and Inventory (link parts to tasks).
    • The role: own the data and AI roadmap, write epics with acceptance criteria, define analytics for agent interfaces.

    All 112 notes are synthetic, written and labelled by me to look like real fibre repair notes. I also wrote the rules baseline, which is why 32 holdout notes were written only after the rules were frozen in git. Treat the numbers as a first look, not a benchmark.
